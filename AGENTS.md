# Agent instructions

This repository holds agent skills for RO-Crate. Each skill lives in `skills/<skill-name>/SKILL.md`
(YAML frontmatter with `name` matching the directory and a `description`). Keep skills concise and
accurate to the RO-Crate 1.3 specification. Plugin manifests: `.claude-plugin/`, `.codex-plugin/`,
`.github/plugin/` — keep versions in sync when changing them.

## Working on this repository

- Before writing or revising a skill, read [background/ro-crate-1.3.0-summary.md](background/ro-crate-1.3.0-summary.md) (principles, section index, which spec lines each skill needs), then the relevant line ranges of the chapter files in `background/ro-crate-1.3/` (or find the requirement in `background/ro-crate-1.3/quick-reference.md` and follow its link). For older versions or migration see [skills/ro-crate-compatibility/references/version-differences.md](skills/ro-crate-compatibility/references/version-differences.md) and the 1.0/1.1/1.2 summaries beside it.

- **Never use unreleased `-DRAFT` specifications, contexts or `conformsTo` values** in skills, examples, fixtures or generated crates: no `https://w3id.org/ro/crate/1.x-DRAFT[/context]`, no `...-DRAFT` profile URIs (e.g. Bioschemas `0.5-DRAFT-2020_07_21`; use the `1.0-RELEASE` profiles), and no draft/unreleased versions of any profile. Use released versions only (RO-Crate 1.0-1.3, default 1.3). When *reading* a crate that declares a draft, report it as unreleased and do not copy it into new output. Some spec tables still show `1.2-DRAFT` leftovers; do not copy them. **One exception:** a Bioschemas profile for a type that has no released Bioschemas profile (e.g. Event, BioSample) may be declared in its latest draft version, in the `conformsTo` of the described entity (never the root), with a note that it is not recommended; prefer the released profile whenever one exists (see `skills/ro-crate-bioschemas`). This never applies to RO-Crate specifications, contexts or RO-Crate profiles. `tests/check_repo.py` still rejects `-DRAFT` URIs in skill files, so describe such drafts in words there.
- Add a skill: create `skills/<skill-name>/SKILL.md` only when it is complete (no placeholder text or TODOs: agents load every shipped skill), with `evals/evals.json`; keep frontmatter to `name` and `description` so other agents can read it; put detail in `references/*.md` and helpers in `scripts/` (Python standard library) inside the skill folder, because a skill may be copied on its own; do not link to files outside the skill folder (lowercase-hyphenated name equal to the directory; `description` says what it does and when to use it). Then list it in the README skills table.
- Keep skills short, procedural and spec-accurate; link to https://www.researchobject.org/ro-crate/specification/1.3/ rather than copying it. Never invent identifiers (ORCIDs, DOIs) in examples that look real.
- Bump `version` identically in `.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json`, `.codex-plugin/plugin.json`, `.github/plugin/plugin.json` and `.github/plugin/marketplace.json`.
- Validate: every manifest must parse (`python -m json.tool <file>`), and each `SKILL.md` must have frontmatter `name` and `description`.
- **Frontmatter must be valid YAML.** Always wrap `description` in double quotes (escape `\"` and `\\`): an unquoted value containing `: ` or ` #` breaks parsers and Markdown rendering (GitHub shows a front-matter error and agents may skip the skill). Keep the keys to `name` and `description`. `tests/check_repo.py` fails on unquoted risky values and, when PyYAML is installed, parses the frontmatter with it.
- Run `python tests/check_repo.py` before committing; see [TESTING.md](TESTING.md).
